Low-Level Design: Entity Notifications & Custom Command

1. Overview

Why

The game requires localized, entity-specific visual feedback for lifecycle events (creation, destruction, and cycle completion) without hardcoding logic into global configuration. Additionally, complex custom gameplay systems (like tutorial steps or milestone trackers) need an agnostic mechanism to emit floating text or toast notifications programmatically, without maintaining their own UI bridging logic.

What

SHOW_CUSTOM_NOTIFICATION Command: A new primitive runtime command that accepts a generic presentation payload and spatial coordinates. Custom systems and behavior actions can enqueue this command at will.

Notification Ability: A new blueprint ability allowing designers to configure UI presentations tied strictly to spawn, kill, and cycle triggers.

Flyweight Component: A NotificationsComponent attached to the compiled Blueprint (not duplicated on the entity state), containing the static spawn and kill presentation data.

Behavior Integration: The cycle notification trigger is compiled seamlessly into the entity's cycle reset BehaviorRule as a SHOW_CUSTOM_NOTIFICATION action.

Evaluator Interception: The NotificationEvaluator is updated to intercept the new command and lifecycle commands (SPAWN, KILL), leveraging the flyweight blueprint data and the new telemetry payload to emit UI events.

How

By defining the new command and behavior action, we establish a standardized pipeline for generic UI alerts. The notificationCompiler segregates the triggers: spawn and kill are stored in the Blueprint's component for the NotificationEvaluator to intercept via the flyweight pattern, while cycle is injected as a behavior action directly into the engine's behavior system.

3. Engine Compilers

3.1. Notification Compiler

File: src/engine/compiler/abilities/notificationCompiler.ts (New)

Responsibility: Translate the editor ability into runtime components and behavior actions.

Interface: (draft: Blueprint, config: NotificationAbilityConfig) => void

Logic:

Filter the config for spawn and kill triggers. Assign the resulting array to draft.components.notifications.

Filter the config for cycle triggers.

If cycle triggers exist, locate the primary cycle reset BehaviorRule within draft.components.behavior.rules (identifiable by the \_reset sortKey suffix generated by the cycle compiler).

For each cycle trigger, construct a SHOW_CUSTOM_NOTIFICATION behavior action (mapping the presentation payload) and append it to the reset rule's actions array.

3.2. Compiler Service Integration

File: src/engine/compiler/CompilerService.ts

Responsibility: Execute the notification compilation step during blueprint processing.

Logic: Import and invoke notificationCompiler passing the draft and config.notifications if the configuration is present. Ensure it runs after the cycleCompiler so the \_reset behavior rule exists.

4. Runtime Execution

4.1. Telemetry Context Update

Files: src/engine/runtime/types.ts & src/engine/runtime/runtimeTick.ts

Responsibility: Provide the current snapshot to the telemetry adapter so post-tick evaluators can read the updated world state (required for querying newly spawned entities).

Logic:

Update RuntimeTelemetryAdapter.onCommandsApplied signature to accept (commands: RuntimeCommand[], previousSnapshot: Snapshot, currentSnapshot: Snapshot).

In runRuntimeTick, pass the newly generated snapshot to the telemetry sink.

4.2. Command Handler

File: src/engine/runtime/handlers/ShowCustomNotificationHandler.ts (New)

Responsibility: Act as a sink for the SHOW_CUSTOM_NOTIFICATION command to satisfy the CommandsManager.

Interface: Standard CommandHandler<ShowCustomNotificationCommand>.

Logic: No-op implementation (return;). The command exists exclusively to be recorded in the command buffer for the UI's NotificationEvaluator.

4.3. Behavior Action Executor

File: src/engine/runtime/systems/behavior/actionExecutorShowNotification.ts (New)

Responsibility: Process the behavior action and push the command to the runtime buffer.

Interface: (action: ShowCustomNotificationAction, context: BehaviorContext, commands: CommandBuffer) => void

Logic:

Extract spatial position from context.self using resolvePhysicsPosition(context.self).

Enqueue a SHOW_CUSTOM_NOTIFICATION command containing the action's presentation payload and the resolved position.

Integration: Register the executor in src/engine/runtime/systems/behavior/ActionExecutor.ts.

5. UI Integration & Evaluation

5.1. Notification Evaluator

File: src/ui/runtime/world/living-cards/NotificationEvaluator.ts

Responsibility: Scan the tick's command buffer and translate commands into UI Card events using the flyweight blueprint pattern.

Interface Update: Update evaluateNotifications signature to accept currentSnapshot: Snapshot alongside previousSnapshot and commands.

Logic: Iterate through the provided command buffer:

Case SHOW_CUSTOM_NOTIFICATION:

Extract presentation and position from the payload.

Construct a LivingCardEvent and push to CardEventBridge.

Case SPAWN / SPAWN_BODY:

Resolve the spawned entity from currentSnapshot via the command payload ID.

Fetch the entity's blueprint using currentSnapshot.getBlueprint(entity.blueprintId).

If blueprint.components.notifications exists, filter for trigger === 'spawn'.

Map matching rules to LivingCardEvent using resolvePhysicsPosition(entity) and push to CardEventBridge.

Case KILL:

Resolve the killed entity from previousSnapshot via the command payload ID.

Fetch the entity's blueprint using previousSnapshot.getBlueprint(entity.blueprintId).

If blueprint.components.notifications exists, filter for trigger === 'kill'.

Map matching rules to LivingCardEvent using resolvePhysicsPosition(entity) and push to CardEventBridge.

NotificationAbilityForm Implementation:

Must be a custom composite form, avoiding generic schema fallback renderers.

Render a specific dropdown for the trigger field (spawn, kill, cycle).

Inputs must be strictly bound to the array element using the standard onChange (e.g., updateAbilityItem) propagation to ensure changes are immediately tracked in the ModuleSession without lag or disconnects.

6. Testing Strategy

Following the canonical testing standards, testing will focus on behavior, isolation, and explicit setup, covering Happy Paths, Negative Paths, Edge Cases, and explicitly covering rendering and session saving via Smoke Tests.

6.1 Unit Tests (Logic & Compilers)

File: src/engine/compiler/abilities/notificationCompiler.test.ts (New)

Happy Path: Given a blueprint draft with a cycle ability, when compiled with spawn, kill, and cycle notifications, then components.notifications contains the exact spawn/kill configs, and components.behavior.rules (the \_reset rule) contains the new SHOW_CUSTOM_NOTIFICATION action.

Negative Path: Given a blueprint draft without a cycle ability, when compiled with a cycle notification trigger, then the compiler gracefully ignores the cycle trigger (or logs a warning) and does not crash or throw an error.

Edge Cases: Empty notification configurations arrays do not mutate the draft unnecessarily.

File: src/engine/runtime/systems/behavior/actionExecutorShowNotification.test.ts (New)

Happy Path: Given a BehaviorContext for an entity with spatial coordinates, when the executor is called, then the CommandBuffer receives exactly one SHOW_CUSTOM_NOTIFICATION command with the matching presentation and coordinates.

Negative Path: Given a BehaviorContext for an entity missing physical coordinates, when executed, then it safely falls back to { x: 0, y: 0 } (or omits the position entirely if supported) without throwing a fatal error.

6.2 Integration Tests (Evaluator)

File: src/ui/runtime/world/living-cards/NotificationEvaluator.test.ts (Update)

Happy Path: Given populated currentSnapshot and previousSnapshot holding blueprinted notifications, when SPAWN, KILL, and SHOW_CUSTOM_NOTIFICATION commands are evaluated, then CardEventBridge.drain() yields the exact corresponding LivingCardEvent objects.

Negative Path: Given a SPAWN command for an entity ID that does not exist in the snapshot, the evaluator skips it gracefully without throwing an undefined reference error.

Edge Cases: Multiple notification triggers firing for the same entity on the same tick produce multiple distinct events in the bridge correctly.

6.3 Smoke & UI Tests (Rendering & Stability)

File: src/ui/devtools/editors/blueprint/mode/forms/NotificationAbilityForm.smoke.test.tsx (New)

Render & Save: Verify the custom form renders all inputs (trigger, message, severity, type, icon). Simulating user input on the message field explicitly dirties the ModuleSession and persists the updated value to the underlying cartridge (validating against "changes not saved" bugs).

Stability: Verify that modifying nested objects (e.g., presentation.severity) does not cause infinite React render loops within the AbilityList or SchemaForm contexts.

File: src/ui/runtime/world/living-cards/LivingCardPool.smoke.test.tsx (Update)

World Rendering: Manually inject a SHOW_CUSTOM_NOTIFICATION event into the CardEventBridge. Verify that the React component successfully mounts the card to the DOM, displaying the exact configured text, correct icon, and accurate severity CSS classes without triggering any React render errors.
