LLD: Phase 1 — Compiler Infrastructure & "Cycle" Ability
Status: Approved for Implementation Context: tools_v2_plan.md (Phase 1) Adherence: Strictly follows context-pack.md and tools_v2.md.

1. Executive Summary
   The Why
   We are transitioning the editor from a "Raw ECS Assembly" model to an "Ability-Based Composition" model. This is necessary to reduce the cognitive load of wiring complex behaviors manually and to prevent brittle references (e.g., typos in state keys) from breaking game logic.

The What
We will implement the Compiler Pipeline pattern.

Source of Truth: The \_editor field in a Blueprint will act as the high-level intent definition.

Compilation: A pure transformation function will generate low-level ECS components (behavior, state, powerSink) from the \_editor configuration.

UI: A "Designer Mode" will be added to the Blueprint Editor, allowing users to configure high-level Abilities (starting with "Cycle") instead of raw JSON.

The How
This phase delivers:

Zod schemas for CycleAbility and the root EditorConfig.

The CompilerService core logic.

The CycleCompiler logic.

The DesignerMode UI components.

Integration into the saveBlueprint action.

2. Data Layer Strategy
   2.1. Schema Definitions
   File: src/data/schemas/abilities/cycle.ts (New)

Responsibility: Defines the strict configuration shape for the Cycle ability.

Interface Definition:

CycleAbilitySchema: Zod Object

duration: Number (Min 1, Default 100). The max value for the progress bar.

powerAttribute: Enum ("body" | "mind" | "social", Default "body"). Which power grid to draw from.

powerDraw: Number (Min 0, Default 0). How much power is consumed per tick.

scaling: Boolean (Default false). If true, progress speed scales with state.assignment.total_level.

oneOff: Boolean (Default false). If true, sets a cycle_complete flag upon finishing instead of looping.

File: src/data/schemas/abilities/index.ts (New)

Responsibility: Aggregates all ability schemas into a single editor configuration object.

Interface Definition:

EditorAbilitiesSchema: Zod Object

cycle: Optional(CycleAbilitySchema).

EditorConfigSchema: Zod Object

abilities: EditorAbilitiesSchema (Default empty object).

File: src/data/schemas/blueprint.ts (Modification)

Responsibility: Updates the canonical Blueprint schema to accept the new source of truth.

Change Logic:

Import EditorConfigSchema.

Add \_editor: Optional(EditorConfigSchema) to the BlueprintSchema definition.

Constraint: Must remain optional to ensure backward compatibility with legacy blueprints.

3. Engine Layer: The Compiler
   3.1. Cycle Ability Compiler
   File: src/engine/compiler/abilities/cycleCompiler.ts (New)

Responsibility: A pure function that mutates a Blueprint Draft based on CycleAbilityConfiguration.

Logic:

State Generation:

Ensure draft.components.state exists.

Set state.cycle -> { value: 0, max: config.duration }.

Set state.cycle_active -> { value: true }.

PowerSink Generation:

If config.powerDraw > 0:

Ensure draft.components.powerSink exists.

Set powerSink.baseDemand[config.powerAttribute] = config.powerDraw.

Set powerSink.throttle = 1 (default).

Set powerSink.efficiency = 1 (default).

Behavior Generation:

Rule ID: sys_cycle_advance.

Condition: state.cycle_active EQUALS true.

Action Value Calculation:

Base: global.dt.

If powerDraw > 0: Multiply by state.powerSink.efficiency.

If scaling is true: Multiply by state.assignment.total_level.

Action: MUTATE target state.cycle ADD [Calculated Value].

Display Binding (Optional/Future):

Phase 1 will strictly handle logic. Visual bindings (e.g. associating state.cycle to a specific bar) remain manual or implied by the state component's existing behavior.

3.2. Compiler Service
File: src/engine/compiler/CompilerService.ts (New)

Responsibility: The orchestration entry point. Takes a Blueprint, determines if compilation is needed, and applies all active ability compilers.

Interface:

compile(blueprint: Blueprint): Blueprint

Logic:

Clone: specific structuredClone of the input blueprint to enforce immutability.

Guard: If blueprint.\_editor is undefined, return the clone as-is (Legacy Mode).

Reset Phase:

Filter out existing behavior rules that start with sys\_. This prevents stale compilation artifacts from accumulating.

Note: This implies "System" rules generated by the compiler own the sys\_ namespace.

Apply Phase:

If \_editor.abilities.cycle is present:

Invoke cycleCompiler(draft, config).

Return: The mutated draft.

4. UI Layer: The Designer
   4.1. Designer Mode View
   File: src/ui/devtools/editors/blueprint/mode/DesignerMode.tsx (New)

Responsibility: The high-level view container for configuring Ability state.

Logic:

Connects to BlueprintContext to get the current blueprint ID.

Renders AbilityList.

Renders an "Add Ability" dropdown (currently only "Cycle").

When "Add Ability" is clicked:

Updates session state: \_editor.abilities.[abilityName] = {} (default config).

4.2. Ability List Component
File: src/ui/devtools/editors/blueprint/mode/AbilityList.tsx (New)

Responsibility: Iterates over configured abilities and renders their specific forms.

Logic:

Iterates keys in \_editor.abilities.

If key === 'cycle', renders CycleAbilityForm.

Wraps the form in a ComponentRow or Card for visual separation.

Provides a "Remove" button that deletes the key from \_editor.abilities.

4.3. Cycle Ability Form
File: src/ui/devtools/editors/blueprint/mode/forms/CycleAbilityForm.tsx (New)

Responsibility: Renders the form inputs for CycleAbilitySchema.

Logic:

Receives value (CycleAbility) and onChange callback.

Uses standard atom inputs (NumberField, EnumField, BooleanField).

Updates fields: duration, powerAttribute, powerDraw, scaling, oneOff.

4.4. Blueprint Editor Integration
File: src/ui/devtools/editors/blueprint/editor/BlueprintEditor.tsx (Modification)

Responsibility: Manages the high-level view state (Designer vs. Raw).

Logic:

State: viewMode ("designer" | "raw").

Initialization: If draft.\_editor exists, default to "designer". Else "raw".

Toolbar: Add a toggle button group to switch modes.

Sync Logic:

When switching from "Designer" to "Raw":

Trigger an immediate compilation (compiler.compile(draft)).

Update the session draft with the compiled ECS components (behavior, state, powerSink).

Why: This ensures the user sees the "Real" ECS state in Raw mode, not the stale state.

5. Integration: Store & Persistence
   5.1. Save Action Update
   File: src/ui/devtools/state/moduleStore.actions.blueprints.ts (Modification)

Responsibility: Intercept the save payload to run the compiler.

Logic:

In the saveBlueprint thunk:

Import CompilerService.

const compiled = new CompilerService().compile(blueprintFromSession);

Pass compiled to the io.saveModule method.

Constraint: We persist the result of the compilation to disk. This ensures the runtime doesn't need to know about the compiler; it just loads standard ECS JSON. But we also persist the \_editor field (it's part of the blueprint schema now), so re-opening the editor restores Designer Mode.

7. Migration Plan & Edge Cases
   Legacy Data: Existing blueprints function normally. Opening them defaults to Raw mode.

Manual Edits in Designer Mode: If a user switches to "Raw Mode", manually edits state.cycle, and then switches back to "Designer Mode" and saves, the Compiler will overwrite the manual edits.

Policy: This is intended. \_editor is the source of truth. Generated fields are ephemeral outputs.

Validation: The CompilerService assumes the \_editor data matches the Zod schema. Validation happens at the UI layer (Form inputs).
